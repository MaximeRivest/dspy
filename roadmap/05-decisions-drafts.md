- **D-045 (DRAFT 2026-08-19 — pending Maxime)** — **Weight training enters through a four-verb structural contract; the training host is a placement, never an identity.** An engine may declare, structurally (D-036 admission, no base class): `forward_backward(batch, loss) -> LossReport`, `optim_step(params)`, `save_state(name) -> WeightsRef`, `sample(request)` (≡ `complete` — the on-policy sampler and the inference face are one seam). Hosts sit on a training placement ladder — rung 0 in-process torch (`InProcessEngine`), middle self-hosted training service, outer hosted service (Tinker-class) — bound per LM entry via `endpoint_ref`/`credential_ref`; moving training between hosts is a placement change and does not detach scores (PIR-010 pattern); changed weights detach, as always. The `loss` argument draws from a closed, versioned vocabulary (`cross_entropy | importance_sampling | ppo | …`; `loss_vocabulary` joins the D-024 versions block); custom losses are authored-code leaves with `authored_by` provenance, captured-or-refused. The user never sees renderers, tokens, `Datum` objects, or loss masks: the signature says what the model must emit and the adapter says where those bytes sit in the token stream, so the mask derives mechanically from the rendered exchange. Surface (amended in session): ONE contract-dispatched trainer — `dspy.optim.Train(target, trainset, ...)` — resolving `sgd-1` (loss= required) vs `fit-1` (no loss) from the target entry's structurally declared training contract (the family itself is ruled in D-049); `WeightTune`/`Fit` survive at most as readable aliases. *Why:* the Tinker SDK independently converged on the same four-verb cut (external validation of the seam), and its cookbook is a catalog of hand-work — renderers, masks, envs, rewards, checkpoints — that dspy's signature/adapter/metric/ProgramIR machinery already owns. Design: `roadmap/DESIGN-trainable-lm.md`.

- **D-046 (DRAFT 2026-08-19 — pending Maxime)** — **The devset is an explicit component-12 sub-slot with its own placement ladder and pinned identity; an unpinned dataset yields an unwarranted score.** Rung 0 bakes a content-addressed blob; middle references a receiver-operated store; outer names a remote dataset (HF id + revision) — identity bakes, location binds (§e0-binding verbatim). A score is a claim about a `dataset_identity` (hash/revision); a living/unpinned dataset is a legal binding whose scores are unwarranted by construction — stated, never guessed (the evaluation analogue of `cost = None`). Examples carry `input_keys[]` and, when mined from production, a `provenance` block. Not-bake reasons are the genuinely-external axes only: size, privacy, licensing. Pinning is compiler work, not user ceremony: an omitted revision/snapshot resolves NOW and bakes pinned — the syntax may say "current", the manifest never does. *Why:* the spec pinned the metric but left the devset implicit, and fixed point 2 (§e2) is unenforceable over a mutable-by-the-back-door objective. Design: `roadmap/DESIGN-eval-data.md` §1.

- **D-047 (DRAFT 2026-08-19 — pending Maxime)** — **Dataset ETL is a closed, versioned verb vocabulary — a pipeline as plain data between the source and the signature.** Verbs — dplyr names wherever dplyr semantics apply, dspy names for what dplyr never covered: `rename, select, filter, mutate` (absorbing coercions via a named coercion-function table), `slice_sample, shuffle, split, designate_inputs` (all seeded); joins and `group_by`/`summarise` deferred until a real case forces ratification (the ReplaceField discipline; aggregation also breaks single-row provenance). The `filter`/`mutate` expression slots are the ratified **node-set expression subset** (D-034/D-037 — no statements, no leaf calls) plus column refs — one grammar shared with forwards, already implemented by the Go/TS interpreters — and sit on their own 3-rung ladder: rung 0 the closed grammar (baked, hash-verifiable); middle an authored pure UDF step (captured-or-refused, rung-walkable per D-022/D-040); outer **pushdown** — the rung-0 expression compiled to the store's language (SQL, HF filters), executing where the data lives, with `result_hash` as the invariant oracle across all rungs. Every verb is pure and seeded, so `source_identity ⊕ pipeline ⇒ result_hash` is checkable: the artifact bakes all three and load re-runs and verifies — declare, don't discover; grade-1 readers validate pipeline shape, grade-2 engines execute and verify. Authored-code steps break static cross-language verification for that pipeline visibly. The tree encoding is the node-set JSON vocabulary plus one new node, `Col` (column reference, row-scope sibling of `Var`). **The authoring surface is the dpyr chain** (`MaximeRivest/dpyr`: dplyr verbs as Python method chains, `col` proxy, polars/duckdb backends, semantics differentially verified against real dplyr) under a strict three-role split: dpyr is frontend (the chain builds the tree) and grade-2 engine (polars at rung 0, duckdb pushdown at the outer rung); the closed IR tree is the only serialized truth. Integration seam: (1) plan export — the chain yields the closed tree as plain data, never backend expression objects; (2) vocabulary gate — out-of-vocabulary verbs (`group_by`, joins, windows) run in dpyr but refuse loudly at export naming the verb and `etl_version`, and their eventual admission takes dpyr's dplyr-verified semantics as candidate; (3) semantics pins — dpyr/dplyr govern the verb layer (NA/None row handling), node-set governs scalar arithmetic, edge divergences ruled in the fixture corpus under dpyr's `SEMANTICS.md` discipline (differential golden files + cross-engine fuzzing). `etl_version` joins the versions block. Pipeline knobs are objective-side: frozen inside an optimization run (fixed point 2), movable only by the D-048 outer loop. *Why:* without the pipeline, "pinned dataset" pins the raw source while the metric consumes transformed rows — the identity would name the wrong bytes; and the closed-verb form keeps the mapping diffable, portable, and cheap to port (the Starlark move at the data layer). Design: `roadmap/DESIGN-eval-data.md` §2.

- **D-048 (DRAFT 2026-08-19 — pending Maxime)** — **Metric/devset evolution is an outer-loop optimization with a human-owned meta-objective; the fixed point is per loop.** The inner loop never touches its objective (§e2 unchanged). A second loop — legitimately a dspy program — mines production traffic (View-2 overlays in a run-log store, which stays OUTSIDE the artifact: View 2 remains never-baked, never load-bearing), ingests feedback into provenance-carrying candidate examples, and proposes devset/metric updates as recorded diffs. The metric is a program, so its evolution is an ordinary optimization run whose own untouchable objective is agreement with human feedback labels — Goodhart is pushed up one level and the regress terminates at a human via the deviation doctrine. An objective change detaches historic scores (scores attach to configurations); kept checkpoints re-score under the new objective (cheap under §c1), and the View-3 trajectory crosses a labeled **objective-boundary node** ("metric v3→v4, devset A→B") so score curves are never read across the boundary by accident. Continuous cadence is a scheduler around batch propose→score→keep; the IR sees only snapshots and diffs. *Why:* objectives drift with the world; the alternative to a governed outer loop is silent redefinition of success. Amended per STUDY-model-contract F6/F7: the loop is additionally load-bearing for two model families — online learners (an hourly re-fit IS this loop at small cadence) and RL policies (feedback mining IS RLHF data collection) — under the cadence law: continuous learning at any cadence, unrecorded learning at none — this makes "the metric evolved" an auditable trajectory event in the same currency (hashed snapshots, labeled diffs, warranted scores) as every other change. Design: `roadmap/DESIGN-eval-data.md` §3.

- **D-049 (DRAFT 2026-08-19 — pending Maxime)** — **ProgramIR is a general learned-program IR; the LM leaf is its richest special case; new model kinds enter through existing slots, never new components.** The general record, v2 (corrected in review — the objective never lives inside the model): **a leaf = signature + adapter + model binding; a model entry = weights + engine + contract + placement + the D-045 training verbs — exactly as dumb as an LM entry.** Objectives (dataset-pool ref + ETL, metric ref, loss, seed-regime) are TRAINING STATEMENTS and attach at the binding/optimizer level (§b-pools: what training means is bindings + tags, never entry-internal — a shared entry with an internal objective cannot state whose loss trains it). The adapter axis is NOT LM-specific: a promptable vision model (SAM: point/box/text prompts → masks) binds a spatial-prompt adapter whose prompt axis opens to optimization exactly like an LM's; a plain embedder binds the IDENTITY adapter — the degenerate case, not a different architecture. The model's request contract decides which optimizable axes exist (lm15's part vocabulary already covers most multimodal requests); a plain tensor-in model's only axis is `weight-ref`. Carried over unchanged: safetensors slot + ties + `weights_identity`, base ⊕ delta, placement ladder, the D-045 four verbs (`sample`→`predict`), `checkpoint = save`, `optimizable ⊆ baked`, D-013 seed regimes as the leaf-local objective. Cross-language model leaves compose from ratified machinery: D-025 language tag + per-language env blocks (R `renv.lock`, Julia `Project.toml`/`Manifest.toml` as new instances), D-022 rung-walk, D-040 requirements gradient, D-042 sealed-Arrow data plane; training a foreign leaf happens where its language lives (rung 0 unsatisfiable by definition — the ladder answers normally). **Datasets become a named pool** (§b-pools shape): program-level component 12 and leaf objective blocks bind entries from it, each entry carrying `dataset_identity` + ETL + rungs — D-046/D-047 apply recursively per leaf with zero new machinery. Recursion is safe because fixed points are per loop, per level: leaf objectives are means (optimizable, forkable); the program's metric + devset stay the untouchable ends; the regress terminates at the human owning the top objective (D-048). Serialization floor stated honestly: tensors → safetensors; classic-ML inference → ONNX; trainable classic ML → authored code + declared format (e.g. `state_format: "rds"`), captured-or-refused, visibly outside the bit-for-bit story. **Contract families, both axes:** request faces form a closed family (`lm15/chat-1 | embed-1 | segment-1 | predict-1 | …`) — one entry shape, the `contract` field declares the typed face, admission structural against it (D-036); lm15/chat is the richest member, and capabilities migrate INTO it by the roles-governance loop (polyfill strategy today → native part when providers converge — a vocabulary version event, never pre-emptive cramming). Training contracts form the sibling family (`sgd-1` = the D-045 four verbs, client-held loop; `fit-1` = `fit(dataset) → state`, host-held loop of length one) — both instances of the **Tinker cut** (client states objective + holds state refs; host owns hardware, execution, failures) at different loop grains, bound on the training ladder like any placement (the R sidecar is a loader-materialized micro training host; Tinker-class services are outer-rung vendor bindings of `sgd-1`). **Flex consequence:** implementation swaps ACROSS contract families — code (any language) ↔ fitted classic ML ↔ deep/finetuned model ↔ LM Predict ↔ bloomed sub-module, at one frozen signature seam — are ordinary `structure`/`choice` moves, optionally composed with a training statement (swap-then-fit = distillation as a search move), gated entirely by existing machinery: static admissibility (signature/contract/D-040 requirements) before any spend, checkpoint = save per candidate, the baked metric + pinned devset as judge, the §e2 cost regularizer on blooming, D-043 floors + invariance-refusal for synthesized bodies, and every move a labeled View-3 diff. **Surface unification:** the leaf binding kwarg is `model=` uniformly (`lm=` retired — two kwargs would force the user to know the face before binding, which deduction exists to remove); `dspy.Model(...)` is the general constructor with the face resolved from identity (provider string / causal-LM architectures ⇒ chat, HF pipeline metadata ⇒ embed/segment, source-file path ⇒ authored + language from extension); `dspy.LM(...)` survives as chat-face-asserting sugar over the same pool-entry object (D-011 layering — one object, two spellings; chat-capability kwargs refuse on a non-chat face). Open byte-shape question flagged for the contract repo, not improvised: whether the manifest pool key `8_lm` generalizes to a model pool key — rides this decision's ratification. **The format vocabulary** is a closed, versioned table — the weights-slot analogue of the ETL verb table: `gguf ⇒ chat/llama.cpp · safetensors-dir ⇒ face from config.json · onnx ⇒ face from graph I/O · skops/joblib ⇒ predict-1/sklearn · rds ⇒ predict-1/R` — each entry naming container, engine, face-deduction rule, and identity grade (content hash everywhere; bit-for-bit: safetensors yes, declared formats stated). **Receiver surface:** `dspy.load(path, place={leaf: ENDPOINT_REF})` (same-identity re-placement — a binding, scores hold, PIR-010), `prog.rebind(leaf=entry)` (identity deviation — recorded, scores detach), `prog.rescore()` (re-warrant via the baked metric) — three verbs, one spec concept each. **The no-training guarantee:** a program authored with zero objective machinery (no dataset/metric/loss/tags anywhere in the file) exports a complete artifact with every axis present untagged — attaching a metric + trainset later requires zero rewrite; the everyday author never pays for learning machinery until wanted, and on that day the program is already the search space. *Why:* every primitive the generalization needs — data, metrics, ETL, optimizers, placement — was defined without reference to language models; the LM was the first and hardest inhabitant of a general structure, and admitting the rest is governance (vocabulary growth by ratification), not construction. Design: `roadmap/DESIGN-trainable-lm.md` §model-leaves.

- **D-050 (DRAFT 2026-08-19 — pending Maxime)** — **Declare-don't-discover governs the ARTIFACT, not the syntax: the frontend deduces everything mechanical; the compiler bakes every deduction as a resolved decision with provenance; ambiguity refuses loudly.** The precedent is `adapter.config` ("resolved: plain_messages", recorded at bake) promoted to a general frontend law. A deduction is admissible iff it is (a) deterministic, (b) baked with provenance (`explain` shows `contract: embed-1, resolved_from: hf:pipeline_tag`), (c) a loud refusal on ambiguity — never a silent guess. The ruled deduction table: **contract face** from model identity metadata (provider string / causal-LM architectures ⇒ chat; HF pipeline metadata ⇒ embed/segment; file format per the D-049 format vocabulary); **authored-vs-packaged** from argument shape (`hf:`/provider ⇒ packaged; source-file path ⇒ authored; weights dir ⇒ local bake — the dspy.LM rule generalized); **language** from file extension (inline `source=` parses or refuses); **training contract** structurally (which verbs the engine declares, D-036 style); **adapter** defaulted from the resolved face (chat ⇒ preset chat; embed/predict ⇒ identity; explicit only to override); **role** defaulted from shape (`Image` ⇒ media — already ratified, D-011/D-012); **dataset revision** resolved-now-pinned-at-bake (D-046); **isolation floor + state_format** defaulted from trust profile + language (D-040/D-043). The irreducible intent set — what the user must always type because no machine may choose it: **signatures and roles, objectives (trainsets/losses/metrics/judges), purity claims (`effects=`), capability facts (`native_fc=`, `device=`), seeds on data operations, and trust tightenings.** Two views, one file: minimal to write, explicit to read — the terse syntax never produces an implicit manifest. *Why:* every review pass on the exemplar removed a keyword by finding its deterministic source; what remained is exactly intent — evidence the line is real, not aesthetic. Exemplar: `roadmap/exemplar-program-everything.py` §9–§12.
