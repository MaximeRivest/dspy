- **D-045 (DRAFT 2026-08-19 — pending Maxime)** — **Weight training enters through a four-verb structural contract; the training host is a placement, never an identity.** An engine may declare, structurally (D-036 admission, no base class): `forward_backward(batch, loss) -> LossReport`, `optim_step(params)`, `save_state(name) -> WeightsRef`, `sample(request)` (≡ `complete` — the on-policy sampler and the inference face are one seam). Hosts sit on a training placement ladder — rung 0 in-process torch (`InProcessEngine`), middle self-hosted training service, outer hosted service (Tinker-class) — bound per LM entry via `endpoint_ref`/`credential_ref`; moving training between hosts is a placement change and does not detach scores (PIR-010 pattern); changed weights detach, as always. The `loss` argument draws from a closed, versioned vocabulary (`cross_entropy | importance_sampling | ppo | …`; `loss_vocabulary` joins the D-024 versions block); custom losses are authored-code leaves with `authored_by` provenance, captured-or-refused. The user never sees renderers, tokens, `Datum` objects, or loss masks: the signature says what the model must emit and the adapter says where those bytes sit in the token stream, so the mask derives mechanically from the rendered exchange. *Why:* the Tinker SDK independently converged on the same four-verb cut (external validation of the seam), and its cookbook is a catalog of hand-work — renderers, masks, envs, rewards, checkpoints — that dspy's signature/adapter/metric/ProgramIR machinery already owns. Design: `roadmap/DESIGN-trainable-lm.md`.

- **D-046 (DRAFT 2026-08-19 — pending Maxime)** — **The devset is an explicit component-12 sub-slot with its own placement ladder and pinned identity; an unpinned dataset yields an unwarranted score.** Rung 0 bakes a content-addressed blob; middle references a receiver-operated store; outer names a remote dataset (HF id + revision) — identity bakes, location binds (§e0-binding verbatim). A score is a claim about a `dataset_identity` (hash/revision); a living/unpinned dataset is a legal binding whose scores are unwarranted by construction — stated, never guessed (the evaluation analogue of `cost = None`). Examples carry `input_keys[]` and, when mined from production, a `provenance` block. Not-bake reasons are the genuinely-external axes only: size, privacy, licensing. *Why:* the spec pinned the metric but left the devset implicit, and fixed point 2 (§e2) is unenforceable over a mutable-by-the-back-door objective. Design: `roadmap/DESIGN-eval-data.md` §1.

- **D-047 (DRAFT 2026-08-19 — pending Maxime)** — **Dataset ETL is a closed, versioned verb vocabulary — a pipeline as plain data between the source and the signature.** Verbs — dplyr names wherever dplyr semantics apply, dspy names for what dplyr never covered: `rename, select, filter, mutate` (absorbing coercions via a named coercion-function table), `slice_sample, shuffle, split, designate_inputs` (all seeded); joins and `group_by`/`summarise` deferred until a real case forces ratification (the ReplaceField discipline; aggregation also breaks single-row provenance). The `filter`/`mutate` expression slots are the ratified **node-set expression subset** (D-034/D-037 — no statements, no leaf calls) plus column refs — one grammar shared with forwards, already implemented by the Go/TS interpreters — and sit on their own 3-rung ladder: rung 0 the closed grammar (baked, hash-verifiable); middle an authored pure UDF step (captured-or-refused, rung-walkable per D-022/D-040); outer **pushdown** — the rung-0 expression compiled to the store's language (SQL, HF filters), executing where the data lives, with `result_hash` as the invariant oracle across all rungs. Every verb is pure and seeded, so `source_identity ⊕ pipeline ⇒ result_hash` is checkable: the artifact bakes all three and load re-runs and verifies — declare, don't discover; grade-1 readers validate pipeline shape, grade-2 engines execute and verify. Authored-code steps break static cross-language verification for that pipeline visibly. The tree encoding is the node-set JSON vocabulary plus one new node, `Col` (column reference, row-scope sibling of `Var`). **The authoring surface is the dpyr chain** (`MaximeRivest/dpyr`: dplyr verbs as Python method chains, `col` proxy, polars/duckdb backends, semantics differentially verified against real dplyr) under a strict three-role split: dpyr is frontend (the chain builds the tree) and grade-2 engine (polars at rung 0, duckdb pushdown at the outer rung); the closed IR tree is the only serialized truth. Integration seam: (1) plan export — the chain yields the closed tree as plain data, never backend expression objects; (2) vocabulary gate — out-of-vocabulary verbs (`group_by`, joins, windows) run in dpyr but refuse loudly at export naming the verb and `etl_version`, and their eventual admission takes dpyr's dplyr-verified semantics as candidate; (3) semantics pins — dpyr/dplyr govern the verb layer (NA/None row handling), node-set governs scalar arithmetic, edge divergences ruled in the fixture corpus under dpyr's `SEMANTICS.md` discipline (differential golden files + cross-engine fuzzing). `etl_version` joins the versions block. Pipeline knobs are objective-side: frozen inside an optimization run (fixed point 2), movable only by the D-048 outer loop. *Why:* without the pipeline, "pinned dataset" pins the raw source while the metric consumes transformed rows — the identity would name the wrong bytes; and the closed-verb form keeps the mapping diffable, portable, and cheap to port (the Starlark move at the data layer). Design: `roadmap/DESIGN-eval-data.md` §2.

- **D-048 (DRAFT 2026-08-19 — pending Maxime)** — **Metric/devset evolution is an outer-loop optimization with a human-owned meta-objective; the fixed point is per loop.** The inner loop never touches its objective (§e2 unchanged). A second loop — legitimately a dspy program — mines production traffic (View-2 overlays in a run-log store, which stays OUTSIDE the artifact: View 2 remains never-baked, never load-bearing), ingests feedback into provenance-carrying candidate examples, and proposes devset/metric updates as recorded diffs. The metric is a program, so its evolution is an ordinary optimization run whose own untouchable objective is agreement with human feedback labels — Goodhart is pushed up one level and the regress terminates at a human via the deviation doctrine. An objective change detaches historic scores (scores attach to configurations); kept checkpoints re-score under the new objective (cheap under §c1), and the View-3 trajectory crosses a labeled **objective-boundary node** ("metric v3→v4, devset A→B") so score curves are never read across the boundary by accident. Continuous cadence is a scheduler around batch propose→score→keep; the IR sees only snapshots and diffs. *Why:* objectives drift with the world; the alternative to a governed outer loop is silent redefinition of success — this makes "the metric evolved" an auditable trajectory event in the same currency (hashed snapshots, labeled diffs, warranted scores) as every other change. Design: `roadmap/DESIGN-eval-data.md` §3.

- **D-049 (DRAFT 2026-08-19 — pending Maxime)** — **ProgramIR is a general learned-program IR; the LM leaf is its richest special case; new model kinds enter through existing slots, never new components.** The general record: **a trainable leaf = signature + implementation + optional objective block `{dataset-pool ref + ETL, metric ref, loss, seed-regime}`** — LM-Predict is that record plus the prompt axis (adapter/instructions/demos); embedders, rerankers, classifiers, and foreign-language models (R, Julia) are the same record with fewer axes, their only optimizable kind `weight-ref`. Carried over unchanged: safetensors slot + ties + `weights_identity`, base ⊕ delta, placement ladder, the D-045 four verbs (`sample`→`predict`), `checkpoint = save`, `optimizable ⊆ baked`, D-013 seed regimes as the leaf-local objective. Cross-language model leaves compose from ratified machinery: D-025 language tag + per-language env blocks (R `renv.lock`, Julia `Project.toml`/`Manifest.toml` as new instances), D-022 rung-walk, D-040 requirements gradient, D-042 sealed-Arrow data plane; training a foreign leaf happens where its language lives (rung 0 unsatisfiable by definition — the ladder answers normally). **Datasets become a named pool** (§b-pools shape): program-level component 12 and leaf objective blocks bind entries from it, each entry carrying `dataset_identity` + ETL + rungs — D-046/D-047 apply recursively per leaf with zero new machinery. Recursion is safe because fixed points are per loop, per level: leaf objectives are means (optimizable, forkable); the program's metric + devset stay the untouchable ends; the regress terminates at the human owning the top objective (D-048). Serialization floor stated honestly: tensors → safetensors; classic-ML inference → ONNX; trainable classic ML → authored code + declared format, captured-or-refused, visibly outside the bit-for-bit story. *Why:* every primitive the generalization needs — data, metrics, ETL, optimizers, placement — was defined without reference to language models; the LM was the first and hardest inhabitant of a general structure, and admitting the rest is governance (vocabulary growth by ratification), not construction. Design: `roadmap/DESIGN-trainable-lm.md` §model-leaves.

- **Thesis amendment (DRAFT 2026-08-19 — pending Maxime; target: `IR-program-spec.md` §a and/or `01-mental-model.md`)** — Proposed one-paragraph account of the whole object, every clause mapping to a ratified or drafted decision: *"A ProgramIR is one serializable value that orchestrates polyglot code leaves and learnable models into a single logical program — distributable across heterogeneous compute by binding, not rewrite — whose every learnable part is baked, searchable, and scored against cost, accuracy, latency, and security, and whose objective itself evolves from production feedback in a governed outer loop that always terminates at a human."* (Clause map: polyglot leaves = D-022/D-025; learnable ⊆ baked = L-invariants; distribution-by-binding = §e0/PIR-010; four scored axes = §e1 + §e3; outer loop terminating at a human = D-048.)
